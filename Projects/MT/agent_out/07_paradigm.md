## Bug: "press space" does not advance (live-run diagnosis)

Reported by the user (2026-09-25) while running
`hover_up_click_007b_review_lastrun.py`: pressing space does not advance the
experiment.

### Evidence (from the user's own run, subject 246049, 2026-09-25 20:38)

`data/246049_go_nogo_dm_2026-09-25_20h38.51.407.log`:

```
0.0276  INFO  Keyboard events cleared          <- welcome_resp.clearEvents on flip
0.0275  EXP   welcome_text: autoDraw = True    <- welcome screen drawn
1.0453  EXP   Device response: <KeyPress ... value=space ...>
1.0457  DATA  Keypress: space                  <- ioHub saw the press
6.7500  DATA  Keypress: space                  <- 2nd press, no advance
11.1871 DATA  Keypress: space                  <- 3rd press, no advance
11.5374 DATA  Keypress: escape                 <- user quits
11.5539 EXP   welcome_text: autoDraw = False   <- still on welcome at quit
```

`data/246049_...csv` (219 B): the **only** routine that recorded a start is
`welcome` (t=0.0109). `instruction.started`, `instruction_2.started`,
`expStart.started` are all empty. The experiment **never left the welcome
screen**, despite three space keypresses.

So the keypress **is** registered by ioHub (`Keypress: space`), but the welcome
routine **does not end**.

### The scripts are the same code

`hover_up_click_007b_review_lastrun.py` and `go_nogo_dm.py` differ in only two
lines (the Builder "generated on" date and the `originPath` string); both set
`expName = 'go_nogo_dm'` (line 43). So the data prefix `go_nogo_dm` in the
user's run is expected for both files — it is not a clue.

### Root cause

The welcome routine's keyboard wait (lines 657–665):

```python
if welcome_resp.status == STARTED and not waitOnFlip:
    theseKeys = welcome_resp.getKeys(keyList=['space'],
                                     ignoreKeys=["escape"], waitRelease=False)
    ...
    if len(_welcome_resp_allKeys):
        continueRoutine = False      # a response ends the routine
```

This is stock PsychoPy Builder code and is correct. It advances **only** when
`getKeys()` returns a key, and `getKeys()` returns a key **only** if it is
still in ioHub's event queue at the moment `getKeys()` runs.

`waitRelease=False` is the culprit. With it, `getKeys()` reports a key while
the physical key is still **held down** and removes it from the queue the first
time it is polled. The welcome routine calls `getKeys()` **once per video
frame** (~16 ms). A human "press" holds a key ~100–400 ms. The sequence is:

1. welcome starts; `welcome_resp.clearEvents` clears the queue on the next flip
   (logged at t=0.0276).
2. User presses and **holds** space. The key is in the queue.
3. On the very first `getKeys()` after the flip, the key is found and **eaten**.
   If that single poll lands on a frame where the event is not yet visible, or
   the key is registered but not returned on that poll, the key is gone.
4. On every subsequent frame the queue is empty, so `getKeys()` returns `[]`
   forever, `continueRoutine` stays `True`, and the routine loops. The user
   presses again and again — each new press is also eaten on its first poll and
   never returns.

This is a **race condition that depends on how long the key is held versus the
frame rate**. On the acquisition machine it evidently worked (a press is caught
within the hold window); on the user's machine it does not. `waitRelease=True`
is the robust setting: the key is returned on the poll that detects it being
**released** and stays in the queue until then, so a normal short press is
guaranteed to be caught.

This affects **every** `waitRelease=False` keyboard routine in the script
(welcome, instruction, instruction_2, expStart, block breaks, pause), so the
same stall can happen at any "press space to continue" step.

### Proposed fix (needs human approval — applied to a copy, not in place)

Change the keyboard waits in the "press space to continue" routines from
`waitRelease=False` to `waitRelease=True`:

```python
theseKeys = welcome_resp.getKeys(keyList=['space'],
                                 ignoreKeys=["escape"], waitRelease=True)
```

Per the agent rules I will **not** edit the project's original PsychoPy file
without agreement, and any fix goes into a copy named
`hover_up_click_007b_review_lastrun_fixed.py`. The trial-level response keys
(left/right) use `waitRelease=False` on purpose (RT is measured to the key
press) and must **not** be changed.

### Alternative (no code change)

If the user prefers not to modify the paradigm, the immediate workaround is:
**press and hold space for ~0.5 s** so the key is held across multiple frames;
the `waitRelease=False` poll will then reliably catch it.

Extracted from `hover_up_click_007b_review_lastrun.py`:

- **Boxes:** `start_box` / `start_box_2` at `(0, -400)`, 100×100 px, grey;
  `response_box` at `(200, 300)`, 100×100 px, white.
- **Initiation threshold:** 5 px above start-box centre (`y = -395`).
- **Threshold routine:** `max_wait_time = 5.0 s`; corridor width 300 px.
- **Stimulus routine:** `max_response_time = 1.5 s`.
- **Go digits:** {2, 3, 4, 6, 7, 8} — click the response box.
- **No-Go digits:** {1, 9} — stop, do not click.
- **No-Go stop logic:** correct if `max_distance < 5 px` and
  `still_duration >= 0.5 s`.
- **ITI:** uniformly random from `[0.5, 0.6, 0.7, 0.8, 0.9, 1.0]` s.
- **Sequence:** 3 Go + 3 No-Go trials per half; No-Go trials spaced ≥ 2 apart.
- **Accuracy labels:** Go → `correct_go` / `failed_go`; No-Go →
  `correct_nogo_stopped` / `correct_nogo_never_moved` / `failed_nogo`.
- **Window:** 1280×800 px.

### Structure

1. Intro (code-drawn text, no image assets) — advance with SPACE.
2. Practice: 3 Go + 3 No-Go trials.
3. Break: "You are halfway done." / "Sie sind bei der Hälfte."
4. Test: 3 Go + 3 No-Go trials.
5. End: "Thank you for participating." / "Vielen Dank für Ihre Teilnahme."
